# Branch Context Ownership Manifest

**Status:** Task 21 implementation contract  
**Scope:** React pages, frontend services, reports, mutations, caches, scheduled work, and vertical workflows.  
**Rule:** Operational data always belongs to one selected, assigned branch. Product, customer, supplier, employee and configuration masters belong to the business. `All Branches` is an assignment-bounded, manager-only, read-only analytics scope.

## 1. Context classes

| Class | Meaning | Read contract | Write contract |
| --- | --- | --- | --- |
| **Branch-scoped (B)** | Physical or financial work performed at one outlet | `getActiveBranchId()`; no branch means empty/fail closed | `requireActiveBranchId()`; IDs supplied by callers must equal the active branch, except the two-ended transfer workflow |
| **Business-wide (W)** | Canonical master/configuration shared by all outlets | No branch predicate | May be edited only in operational branch context; the global DB guard rejects every write while `All Branches` is active |
| **Manager aggregate (A)** | Read projection over several branches assigned to the signed-in manager | `getAnalyticsBranchIds()` and SQL `IN (...)`; zero assignments means `1 = 0` | Never writable |
| **Mixed (M)** | A business-wide master with branch-owned facts | Master query is W; stock, sales, appointments, balances, history or availability panels are B | Each mutation follows the table it changes |

`getActiveBranchId()` intentionally returns `null` in `All Branches`, before branch assignment has loaded, and for an unassigned user. It never fabricates `default-branch`. `requireActiveBranchId()` is the only valid branch source for operational mutations.

## 2. Authoritative data-set inventory

### Branch-scoped operational tables (B)

- Core/POS: `sales`, `sale_returns`, `payments` through their sale, `cash_register`, `expenses`, `petty_cash`, `customer_payments`, `supplier_payments`, `batches`, `stock_takes`, `purchase_orders`, goods receipts through their PO/batches, `bank_transactions`, branch-owned `bank_accounts`, `stock_transfers` (both endpoints).
- Documents: `invoices`, `quotations`, `credit_notes`, `recurring_invoice_templates` and their child rows through the parent document.
- HR operations: `attendance`; payroll runs are B when `branch_id` is present and A only in the manager reporting flow.
- Retail: `shrinkage`, `laybys`, `special_orders`; child items/payments inherit the parent branch.
- Hospitality: `dining_areas`, `dining_tables`, `kitchen_stations`, `menu_items`, `hospitality_orders`, `room_types`, `rooms`, `bookings`, `reservations`, `hospitality_wastage`, service periods and branch-owned folio/order facts. Guests remain W.
- Salon: `salon_appointments`; appointment services, commissions, back-bar consumption and checkout inherit the appointment/sale branch. Service/staff/resource catalogues remain W.
- Hardware/equipment: `quotations`, `delivery_notes`, `equipment_units`, `service_jobs`, rentals and stock batches. Product specifications remain W.
- Dawa: dispensing/sales, controlled movements, cold-chain readings/units where a branch is present, claims generated by branch transactions, refill work queues and stock/expiry facts. Drug, patient, prescriber, insurer and compliance configuration masters remain W.
- Audit/queues: operational audit rows, eTIMS invoice queue rows, offline mutations and notification work inherit the source transaction branch.

### Business-wide masters (W)

`products`, categories, brands, variants and UOM definitions; `customers` and patient/client profile identity; `suppliers`; users, roles, groups and permissions; employees/departments/leave types; chart of accounts; payment methods/providers; taxes; price-list definitions; insurers and doctors; currencies/country/base currency; module/licence configuration; print, receipt, scanner, display, network, backup, update, AI and hospitality settings; branches and user-branch assignments themselves.

A W master can contain branch-specific derived facts. Examples: product stock is B via `batches`; customer sales/credit history is B; supplier purchasing history is B; employee attendance is B.

### Manager aggregates (A)

Branch performance cards, curated analytics (`sales`, inventory value, purchasing and source-linked finance), manager dashboards explicitly using `getAnalyticsBranchIds()`, and assigned-branch comparison. `listAssignedBranchPerformance()` joins through `user_branches`; `runReport()` emits predicates only for assigned IDs. There is no implicit “all rows” aggregate.

## 6. Mutation contract

1. Operational creates capture `requireActiveBranchId()` once and bind it to the inserted row and stock/money effects.
2. Operational updates/deletes first load or predicate the active branch. Explicit `branchId` read options cannot bypass the selected context.
3. Transfers are the only two-branch mutation: create requires active source plus assignments to both endpoints; dispatch requires active source; receive requires active destination; cancel requires active source.
4. `All Branches` sets the central context read-only before publishing the state transition. `lib/db.execute()` rejects every direct or transactional mutation before dispatch.
5. Business-wide products, customers, suppliers and configuration are not branch-filtered. They are still unavailable for mutation while the UI is in the dedicated aggregate analytics scope.
6. No service may substitute a seeded/default branch when the active branch is absent.

## 7. Cache, persistence and stale-request inventory

| State/cache | Class | Switch behavior |
| --- | --- | --- |
| Zustand active branch | Context | Persists only `active`; assignments and aggregate scope are revalidated on sign-in/restart |
| POS cart (`omnix-cart`) | B | Cleared on load, switch, aggregate entry and sign-out |
| Auth effective permissions | B | Reloaded for the new branch; request version prevents stale permission publication |
| App shell route/page state | B | Outlet key includes scope, branch ID and revision, forcing operational pages/POS to reload |
| `useListData` rows/request sequence | B | Revision is a query dependency; cleanup invalidates the previous request sequence |
| DB/local/LAN reads | B/M/W | Generation captured before dispatch and asserted after response; stale branch responses throw `StaleBranchContextError` |
| AI response cache (`ai_cache`) | M | Key includes `branch:<id>`, `all:<assigned ids>` or `branch:none` |
| Hospitality setting caches (`autoFireCache`, `requireRecipeCache`) | W | Not invalidated; values are business-wide settings, not operational results |
| Function-local Maps/sets in reports and pages | Inherit caller | Recreated per call or page remount; never module-level operational caches |
| Cart broadcast timer | B | Cart clear increments revision and broadcasts the empty branch-owned cart |
| Country/theme/density/module/auth persistence | W | Intentionally survives branch switches |

`branch-context.registerBranchCacheInvalidator()` is the extension point for future module-level operational caches. `advanceBranchContext()` invokes registered invalidators before emitting `omnix:branch-context-changed`.

## 10. Legacy schema limitations and fail-closed rules

The following tables predate branch ownership. This task may not edit `src-tauri`, so these are explicit migration blockers rather than implicit business-wide exceptions:

| Legacy table/path | Missing ownership | Current safe behavior | Required migration follow-up |
| --- | --- | --- | --- |
| `prescriptions` before dispense | No `branch_id`; `sale_id` is null while pending | Dispensed prescription-derived reads, refill candidates and reminder queues inherit `sales.branch_id`; a pending prescription cannot be reliably isolated across restart | Add immutable `branch_id` to `prescriptions`, backfill from sales where possible, and require it on create |
| `controlled_log` walk-in rows | No `branch_id`; `batch_id` and prescription can both be null | Register reads expose only rows attributable through an active-branch batch or a prescription sale; unattributable legacy rows fail closed | Add `branch_id` and backfill attributable rows |
| `controlled_disposals` | No `branch_id`; legacy schema allows null `batch_id` | New disposal writes require an active-branch batch; lists inherit through that batch and hide batchless legacy rows | Add `branch_id`, make ownership non-null, and backfill through batches |
| `insurance_batches` | No `branch_id` | Batch lists/settlement inherit through claim sales; mixed-branch legacy batches cannot be settled | Add `branch_id` and enforce same-branch membership |
| `guest_folios` walk-ins | No `branch_id` and no booking parent | Booking folios inherit booking ownership; new walk-ins persist `W-<branchId>-` in `folio_number`; untagged legacy walk-ins fail closed | Add direct `branch_id` and backfill booking/prefixed rows |
| general-ledger headers | No direct branch column | Operational finance reports scope through branch-owned source documents; no unconstrained fallback | Add durable source-branch ownership if standalone journals become branch operational |
| `sales_daily` rollup | No branch dimension | Not used as a source for branch analytics | Replace with a branch-keyed rollup before enabling it in branch reports |

These limitations do not authorize cross-branch writes or All Branches mutations. `src/lib/db.ts` still rejects every frontend mutation in aggregate scope. A future migration must preserve the fail-closed behavior until backfill is complete.

## 11. Review checklist for new code

- Declare B/W/A/M in the service or manifest before adding a query.
- B read: obtain active branch once, return empty/fail if absent, and predicate every operational parent/subquery.
- B write: call `requireActiveBranchId()`; never use nullable accessor, constants or “first branch” fallbacks.
- A read: use only assigned IDs and produce `1 = 0` for an empty assignment list.
- Cache: include `getBranchCacheNamespace()` or register an invalidator.
- Async: rely on DB generation checks and still cancel/sequence React state publication.
- Tests: cover unauthorized explicit IDs and a switch while a read is in flight.
